## Step 2: The pure parser and decision rule
**Goal**: Implement the offsets, the whole-records length check and the errno rule as pure functions, with the architecture statement in the parser's doc comment.
**Implementation Logic**:
1. `parse_kinfo_records(buf)`: `let (chunks, rest) = buf.as_chunks::<KINFO_PROC_SIZE>();` and return `None` unless `rest.is_empty()`. This is the whole-records check; a kernel that returns a partial record is not parsed. Do not write `buf.len() % KINFO_PROC_SIZE != 0` or `chunks_exact(KINFO_PROC_SIZE)`: clippy 1.99 rejects them (`manual_is_multiple_of`, `chunks_exact_to_as_chunks`, both measured), and `as_chunks` is stable since 1.88, the MSRV (`cargo +1.88 check --locked --all-features` passed on a scratch copy). Then per chunk (`chunks.iter()`) `pid = i32::from_ne_bytes(chunk.get(P_PID_OFFSET..P_PID_OFFSET + 4)?.try_into().ok()?)` and `comm = chunk.get(P_COMM_OFFSET..P_COMM_OFFSET + P_COMM_SIZE)?` cut at its first NUL (the 17th byte is always NUL, so a 16-byte name is returned whole). No `buf[i]` (`clippy::indexing_slicing` is denied), no `as` (use the typed arrays above). The 648 and the two offsets are the values the SDK header gives, measured while drafting with `clang -isysroot $(xcrun --show-sdk-path)` (Xcode 26.2, MacOSX SDK) for both `-arch arm64` and `-arch x86_64`: `sizeof(struct kinfo_proc) = 648`, `offsetof(kp_proc.p_pid) = 40`, `offsetof(kp_proc.p_comm) = 243`, `sizeof(p_comm) = 17` (`MAXCOMLEN + 1`).
2. The doc comment on `parse_kinfo_records`, and the module doc, carry the architecture statement, in this form: arm64 (native): the offsets above from the SDK header, and a live `KERN_PROC_PID` read of `launchd` and of the test process on an Apple M3 Pro, macOS 26.6.2. x86_64: the same header probe with `clang -arch x86_64`, and `cargo test --target x86_64-apple-darwin --lib` under Rosetta 2, which runs the live anchor test `kern_proc_pid_record_matches_the_kernel_for_this_process`. Native Intel hardware: untested (`ROADMAP.md` lists Intel Macs as untested hardware); keep `Native Intel hardware: untested` on one line, since the gate greps it and the file is hard-wrapped. A reader must be able to tell which architectures the layout was verified on, which is what R03 asked.
3. `classify_kern_proc_pid(rc, errno, buf, len, pid)`: check `rc` first. `rc != 0` gives `Refused { errno }` and `buf` and `len` are never read. Reason, measured on this machine under profile Q: a refused `sysctl` still leaves `len = 648` and the buffer zeroed, which parses as a record for PID 0. `rc == 0 && len == 0` gives `NoRecord` (measured: a dead PID, `2147483647` and `-1` all return rc 0, len 0). Otherwise `buf.get(..len)` (`None` gives `Unusable`), `parse_kinfo_records`, and exactly one record whose `pid` equals the requested one gives `Record`; anything else (a partial length, two records, another PID) gives `Unusable`, and `Unusable` is "can't tell". Do not use a size probe (`oldp = NULL`): measured, it reports 3888 bytes for PIDs 0, 1 and self and 3240 for PIDs that do not exist, so it carries no existence information.
4. `decide_exists(path, kern_proc_pid)`: `PathLookup::Found` gives `Some(true)` and the closure is not called (libproc answers first, so every case that works today keeps its answer). Otherwise call the closure once: `Record` gives `Some(true)`; `NoRecord` gives `Some(false)`; `Refused` gives `Some(false)` when the path lookup's `errno` is `ESRCH` and `None` otherwise; `Unusable` gives `None`. Defect in R01 to record: it says "if that call is refused too: `ESRCH` → `Some(false)`", but `sysctl` never returns `ESRCH`. The only reading that has an `ESRCH` is `proc_pidpath`'s errno, and it is today's rule for the doubly refused case, so the leaf implements that and says so in the doc comment. A consequence, accepted: PID 0 with both calls refused reads `None` under Q (`proc_pidpath` says `EPERM` there), but it would read `Some(false)` where `proc_pidpath` says `ESRCH` and `sysctl` is refused. That is the documented residual of having no PID 0 special case.
5. Do not remove the Step 1 `#[allow(dead_code)]` (module and `metal.rs` stubs) in this step: on macOS the parser, the classifier and the decision rule are still unused outside the tests until Step 3 wires them in, so removing it here fails `clippy -D warnings` at this commit. Step 3 item 4 removes it, in one place, for the whole module and the `metal.rs` stubs. The six Step 1 portable tests are green from this step on; the three macOS-only ones (`kern_proc_pid_record_matches_the_kernel_for_this_process`, `process_exists_finds_kernel_task_on_macos`, the sandbox table) stay red until Step 3, which is why Steps 1 to 3 are one squash group.
